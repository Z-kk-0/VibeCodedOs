# Hematite – Decisions

Short log of architecture decisions. Per entry: what, why, alternatives.

## Ground rules
- OS from scratch, for learning. One programming language (plus the unavoidable bit of assembly).
- No big external libraries that do the real work (bootloader crates, ready-made paging/interrupt libs, etc.).
- **Not a textbook clone.** The usual path is a reference, not a rule. Where a less common design is better or more interesting, we take it and say why.
- **Multi-core by design.** Hematite must use all CPU cores, and nothing may rely on "only one thing runs at a time" (e.g. "the caller is blocked, so nobody touches its memory"). Exclusivity is enforced with locks, atomics and page tables – on every core.
- **Handover-ready at every commit.** Anyone – human or AI – must be able to pick this up cold. Docs (`CONTRIBUTING.md`, `ARCHITECTURE.md`, this file) change in the same commit as the code they describe. Tooling is plain Rust and cross-platform (`cargo xtask`).

## Coding rules
- **Readable first, but not slow.** Clear code over clever code; only optimize where it measurably matters, and then explain it in a comment.
- **Small files.** One concept per module, soft limit ~200 lines. Bigger → split into a folder module.
- **Names say what things are.** No cryptic abbreviations, except names from the specs (`efi_main`, `GDT`) – those link to the spec.
- **Comments explain why, not what.** Hardware/spec facts cite their source (e.g. "UEFI spec 2.10, §4.3").
- **Every `unsafe` block has a `// SAFETY:` comment** saying why it is sound.
- **Hardware details stay at the edges.** Raw pointers/registers wrapped in small safe types; the rest of the code uses those.
- `cargo fmt` and `cargo clippy` clean. Code and comments in English.

## 001 – Language
**Decision:** Rust, `#![no_std]`, only `core` – no external crates.
**Why:** The compiler catches most memory bugs; hardware access is visibly marked `unsafe`. Cross-compiling for bare metal (`x86_64-unknown-none`) works on Windows without an extra toolchain. Assembly via `asm!`/`global_asm!` – stays one language.
**Alternatives:** C (more transparent, more tutorials, but painful cross-toolchain on Windows, no safety nets). Zig (still too unstable).

## 002 – Target architecture
**Decision:** x86_64.
**Why:** Runs natively on the dev machine, excellent QEMU support, most documentation (OSDev wiki, Intel/AMD manuals).
**Alternatives:** AArch64, RISC-V (cleaner designs without legacy baggage, but further from our hardware). Cost of x86_64: legacy (real mode, segmentation, GDT) we have to deal with.

## 003 – Boot method
**Decision:** Own UEFI loader in Rust (target `x86_64-unknown-uefi`), UEFI structs defined by hand – no `uefi` crate. Tested in QEMU with OVMF firmware.
**Why:** Stays in one language; firmware already hands us 64-bit long mode with paging, so we skip real-mode legacy and focus on memory map, framebuffer and kernel handoff ourselves.
**Alternatives:** Own legacy BIOS loader (lots of 16/32-bit assembly, obsolete firmware). Limine/GRUB via Multiboot2 (fast, but someone else does the learning part).

## 004 – Kernel lives inside the loader
**Decision:** The kernel ELF is embedded into `BOOTX64.EFI` at compile time (`include_bytes!`). One file boots the whole OS.
**Why:** No UEFI file system protocols needed just to find our own kernel; loader and kernel can never be out of sync.
**Alternatives:** Separate `kernel.elf` on the ESP, read via Simple File System protocol (more firmware code, more ways to fail).

## 005 – Position-independent kernel
**Decision:** Kernel is a static PIE (default of `x86_64-unknown-none`). The loader puts it wherever the firmware has free memory and applies the relocations itself.
**Why:** No hard-coded load address that might collide with firmware memory. Relocation is ~50 lines and teaches how linkers/loaders really work.
**Alternatives:** Fixed link address + linker script (simpler, but breaks if that memory is taken). Higher-half mapping – comes later with our own page tables.

## 006 – Kernel knows nothing about UEFI
**Decision:** Loader translates firmware data into our own `BootInfo` (crate `boot_info`, shared by both). Our allocations are tagged with OS-defined UEFI memory types (`0x8000_0000+`) so the map tells the kernel where it lives.
**Why:** Clean boundary: firmware specifics stay in the loader; the kernel could be booted by something else later.

## 007 – First kernel output: serial port
**Decision:** COM1 (16550 UART), polled. Screen output (GOP framebuffer) comes later.
**Why:** ~40 lines, works without any setup, and QEMU pipes it to the host – so boots can be tested headless (`cargo xtask boot-test`).

## 008 – One door for all interrupts
**Decision:** All 256 vectors get a tiny assembly stub (uniform 16-byte slots, generated with `.rept`) that pushes the vector number and jumps to one common path. That path saves *all* registers into an `InterruptFrame` and calls one Rust function, which may modify the frame before `iretq`.
**Why:** One place where every interrupt arrives, with the full CPU state as a plain struct. Later the scheduler can switch tasks just by swapping that frame – no separate context-switch code. Uniform slots mean the IDT is computed (`base + 16·n`), no address table.
**Alternatives:** `extern "x86-interrupt"` functions (unstable Rust, only saves what each handler uses). One hand-written handler per exception (lots of copies, no common frame).
**Also (008):** Double fault runs on its own stack (TSS IST 1), so a broken kernel stack still gets reported. Every boot runs an `int3` round trip; `cargo xtask boot-test --crash` checks that a real page fault is reported.

## 009 – Testing: pure logic on the host, hardware in QEMU
**Decision:** Everything that is just "bytes in, bytes out" lives in small `no_std` library crates (`elf`, `x86`, `boot_info`) that also build for the host, so `cargo test` runs their unit tests in milliseconds. Code that needs the real CPU stays in `kernel`/`loader` and is checked by booting in QEMU. `cargo xtask test` runs all of it.
**Why:** `no_std` only restricts our code, not the test harness. Splitting out pure logic also enforces "hardware at the edges": the `x86` crate *describes* the CPU's formats, `kernel/src/arch` *uses* them.
**Alternatives:** `custom_test_frameworks` to run tests inside the kernel (nightly-only Rust). Making kernel/loader themselves host-testable (lots of `cfg(test)` noise around asm and entry points).

## 010 – Name: Hematite
**Decision:** The OS is called **Hematite** (the repo keeps its name, VibeCodedOs).
**Why:** Hematite is Fe₂O₃ – iron oxide, the mineral that rust is made of. So it's literally "Rust, crystallized": an OS built from Rust, layer by layer. Iron oxide also stored the bits of early computers (ferrite core memory). And `b"HEMATITE"` is exactly 8 bytes – it fits the boot magic number perfectly.
**Alternatives:** Ferrite (an obvious, common pick for Rust projects), Lodestone, Magnetite.
## 011 – Timer: local APIC, measured with the PIT
**Decision:** Periodic local APIC timer at 100 Hz on vector 0x20. Its speed is unknown, so at boot we let it count for 10 ms of PIT channel 2 (polled via port 0x61, no interrupts needed) and scale. The legacy 8259 PICs are remapped to 0x70+ and fully masked.
**Why:** The APIC timer is per-core – the right base for a scheduler later, and for multi-core. The PIT has a fixed 1.193182 MHz clock, so it's a reliable ruler without parsing ACPI tables first.
**Alternatives:** PIT as the tick source (one shared timer, slow I/O ports). HPET for calibration (needs ACPI parsing – later). TSC deadline mode (also needs a known TSC frequency).
## 012 – Architecture: ownership microkernel
**Decision:** Hematite becomes a microkernel. The kernel only manages memory, switches tasks and delivers messages; drivers and services are ordinary programs in their own hardware-protected address spaces (ring 3). Resources are **capabilities** – unforgeable handles to objects (memory, channels, devices, interrupts). The twist: **Rust's ownership rules apply between processes, enforced by the page tables**:
- *move* – sending a page unmaps it from the sender and maps it into the receiver. Zero copies, and the sender really can't touch it anymore.
- *shared borrow* (`&T`) – the page is mapped read-only in both.
- *exclusive borrow* (`&mut T`) – the page leaves the lender until it's returned.
Handles follow the same rules.
**Why:** Unique, yet we still learn all the fundamentals (page tables, user mode, syscalls, context switches). The `InterruptFrame` design (008) already makes task switching a frame swap.
**Alternatives:** Classic monolithic kernel with "everything is a file" (the textbook clone; one driver bug takes down everything). Single address space with Rust-only programs (fast, but teaches little about hardware isolation and trusts the compiler blindly).
**Consequences:** Next comes a physical page allocator, our own page tables and a higher-half kernel, so every process gets the lower half to itself.
## 013 – Tooling in Rust: `cargo xtask`
**Decision:** Build, run and test commands are a small Rust program (`xtask/`, no dependencies), called via a cargo alias: `cargo xtask build | run | boot-test | test`. It replaces the earlier PowerShell scripts.
**Why:** Handover-readiness – works on Windows, Linux and macOS without porting shell scripts, and stays in our one language. Reading the serial log as bytes also fixed PowerShell's encoding issues.
**Alternatives:** PowerShell (Windows-centric), Makefile/just (extra tools, shell differences per OS).
## 014 – Physical memory: a frame table with an embedded free list
**Decision:** Every 4 KiB frame of RAM gets an 8-byte entry with its state (`Unavailable`, `Free`, `Allocated`). Free entries are chained into a list *through the table itself*, so allocate and free are O(1). The table lives in the first usable region big enough (crate `frame_table`, host-tested); access goes through a `SpinLock` that also disables interrupts. Freeing a frame that isn't allocated panics.
**Why:** The ownership model (012) needs to know who each frame belongs to – the state field is where "moved to process X" or "shared by n" will go. Double frees are caught instead of silently corrupting memory. Cost: 0.2 % of RAM.
**Alternatives:** Bitmap (compact, but O(n) search and no room for ownership state). Free list stored inside the free frames (no metadata at all). Buddy allocator (contiguous multi-frame blocks – add later if DMA needs it).
**Also:** Firmware "boot services" memory is a separate `FirmwareReclaimable` kind: it still contains the page tables the CPU uses, so it's only reclaimed after we switch to our own (roadmap step 2). Same for loader memory.
## 015 – Address space: the loader builds it, the kernel starts in the higher half
**Decision:** The loader builds the kernel's page tables before leaving the firmware and switches to them right before the jump. Layout (documented in `boot_info`): kernel image at `0xFFFF_FFFF_8000_0000` (top 2 GiB), all physical memory 1:1 at `0xFFFF_8000_0000_0000` (the "window", 2 MiB pages, at least 4 GiB so device registers are covered), plus a temporary identity map so the loader survives the switch. The kernel deletes the identity map first thing – the whole lower half is then free for user programs – and reclaims firmware and loader memory.
Kernel pages get their ELF segment's permissions: code read-only + executable, data writable + no-execute (W^X), enforced in ring 0 too (CR0.WP, EFER.NXE). The mapping logic is the host-tested `paging` crate, shared by loader and kernel through a small `TableMemory` trait.
**Why:** Our PIE kernel (005) can simply be relocated to the high address – no second position-dependent stage. The loader still has the firmware's allocator, so building tables there is easy; the kernel never runs on firmware page tables. W^X catches whole bug classes (verified once by hand: writing to code → `#PF 0x3`, executing data → `#PF 0x11`).
**Alternatives:** Kernel builds its own tables after starting identity-mapped (needs a self-relocation step). 1 GiB pages for the window (fewer tables, but not every CPU – e.g. QEMU's default model – supports them).
## 016 – Kernel heap: size classes plus whole pages
**Decision:** Requests up to 2 KiB are rounded up to a power of two (16 … 2048 bytes) and served from one free list per size class; free blocks store the list link inside themselves. Bigger requests get whole pages, mapped on demand and returned (frames back to the frame allocator) when freed. The heap has its own 512 GiB region at `0xFFFF_FF00_0000_0000`; logic in the host-tested `heap` crate, `GlobalAlloc` + page mapping in `kernel/src/memory/allocator.rs`. All page-table changes now go through one lock.
**Why:** O(1) allocate/free with no searching, alignment for free (power-of-two blocks in page-aligned pages are aligned to their size), tiny code. Fits a microkernel, whose own allocations are mostly small fixed-size objects (tasks, capabilities, messages).
**Alternatives:** Linked-list first-fit (simple, but O(n) and fragments). Buddy allocator (merges neighbours, but more code for little gain at our sizes). Slab per object type (a refinement of size classes – possible later).
**Limits:** Pages of size classes are kept for reuse, never returned. Heap virtual addresses are not reused (512 GiB of address space is plenty for now). Alignment above 4 KiB is refused.
## 017 – Tasks: a switch is answering an interrupt with another frame
**Decision:** Preemptive round robin, one 10 ms tick per slice. The interrupt dispatcher returns the `InterruptFrame` to resume; the stub loads it into `rsp` before restoring registers. So a task switch is: save the interrupted task's frame pointer, return another task's. Voluntary switches (`sleep`, `exit`) raise `int 0x30` and go through the very same path. A new task gets a 16 KiB heap stack with a hand-made frame on top, so its first "return from interrupt" starts it. The running boot code becomes task 0; an idle task (`hlt`) runs when nobody is ready. Exited tasks are freed at a later switch – never the current one, whose stack we may still be on. Choosing the next task is the host-tested `scheduling` crate.
**Why:** No separate context-switch routine: one path for every way of entering and leaving a task, and the saved state is the same struct exceptions already report. Exactly what 008 prepared.
**Alternatives:** Cooperative switching with a `switch(from, to)` routine saving only callee-saved registers (faster, but no preemption and a second mechanism). Per-priority queues (later, if needed).
**Also:** `println!` now takes a lock so one call is never torn apart by a switch; panic and exception reports use lock-free `emergency_println!`.
## 018 – User mode: own address spaces, one door into the kernel
**Decision:** A user program runs in ring 3 in its own address space: an own lower half (program at `0x40_0000`, stack below `0x7FFF_FFFF_0000` with an unmapped guard page above), the kernel's upper half shared by copying its top-level entries. Programs are position-independent ELFs loaded by the same `elf` crate as the kernel, with W^X plus the user bit, embedded in the kernel until there is a file system. **System calls go through `int 0x80`** – the same interrupt path as everything else: the call is just another `InterruptFrame` (number in `rax`, arguments in `rdi`/`rsi`, result in `rax`), so `sleep` and `exit` switch tasks exactly like the timer. The task switch also loads CR3 and the TSS kernel stack. Pointers from programs are never dereferenced: every page is checked in the program's own tables and copied through the physical memory window. A fault in ring 3 ends that program; only kernel faults stop the machine. Calls: `exit`, `write`, `sleep` (crate `abi`; programs use `userlib`).
**Why:** Keeps the one-door design (008, 017) – no second entry path with its own register conventions and stack switching. Proven at every boot: `programs/intruder` attacks twice (via a system call, then directly) and must be stopped while `programs/hello` keeps running; afterwards both address spaces must be fully freed.
**Alternatives:** `syscall`/`sysret` (much faster, but its own entry path: manual stack switch, `swapgs`, different saved state – worth it once system calls are hot; the GDT order already allows it). One shared address space for all programs (no isolation).
## 019 – Multi-core: the GDT as an ID card, one shared run queue
**Decision:** Hematite starts every core the ACPI MADT lists and schedules tasks on all of them. Decided together with the owner:
- *Finding cores:* the loader only passes the ACPI root pointer (from the UEFI configuration table); the kernel walks RSDP → XSDT/RSDT → MADT itself (host-tested crate `acpi`).
- *Waking cores:* INIT, STARTUP, STARTUP over the APIC. A woken core starts in 16-bit real mode on a page below 1 MiB the loader reserved (`CoreStartup`). The startup code (`arch/smp/startup_code.rs`) leaps from real mode **straight to long mode** – CR4, EFER, then CR0 with protection and paging switched on together, then a far jump into a 64-bit segment – skipping 32-bit protected mode entirely. It copies the boot core's CR0/CR4/EFER, so every core runs with exactly the same settings. Its page tables (second reserved page, below 4 GiB for the 32-bit CR3 load) are the kernel's upper half plus the startup page mapped at its own address; every core switches to the kernel's tables at once, and the extra tables are freed afterwards. Cores start one at a time; each joins the scheduler before the next is woken.
- *Per-core data ("who am I?"):* each core's GDT is the first field of its `PerCore` (GDT, TSS, index, APIC ID). `sgdt` returns the GDT's address = the `PerCore`. No `swapgs`, no "did we come from user mode?" branch in the one interrupt door (008), and ring 3 can't change the GDT register.
- *Scheduler:* one run queue under one lock, but a current task and an idle task per core (`scheduling` crate, generic and host-tested). A started core's own startup code becomes its idle task. Only core 0's timer advances the clock.
- *The handoff problem:* after picking the next task, a core still runs on the *previous* task's stack until the stub loads the new `rsp`. If another core resumed that task meanwhile, both would use one stack. So the previous task gets a `leaving` flag (set under the scheduler lock); the dispatcher returns it next to the frame (`rdx`), and the stub clears it right after switching stacks. Flagged tasks are neither picked nor freed.
- *TLB shootdown:* every address space keeps a bit mask of the cores that have it loaded (set before loading CR3, cleared after leaving). Changing a mapping flushes exactly those cores – for the shared kernel half, all online cores – via an IPI, and waits until all have flushed. Spinning `SpinLock`s serve pending shootdowns, because the waiting sender may hold the very lock a core spins on with interrupts off.
- A kernel panic or exception stops all other cores (IPI to all), so nothing keeps running on broken state.
**Why:** Ground rule "multi-core by design" – and the upcoming ownership IPC relies on page tables enforcing borrows on *every* core, which is exactly what the shootdown provides. The GDT trick is unusual (the textbook uses GS + `swapgs`, a notorious bug and security source, e.g. CVE-2019-1125) and keeps the interrupt path identical for all cores. The direct real→long mode leap needs half the usual startup code.
**Alternatives:** Cores from UEFI's MP Services protocol (less to parse, but teaches nothing we don't need for ACPI anyway). GS base + `swapgs`, or looking up the APIC ID on every access (an MMIO read each time). Per-core run queues with work stealing (scales better, much more logic – later, if the one lock ever shows up in measurements). Broadcasting every shootdown to all cores (simpler, but wakes idle cores for nothing).
**Limits:** At most 64 cores (bit masks). xAPIC mode only, so APIC IDs up to 255. One page per shootdown, one shootdown at a time. If a core doesn't answer within 1 s, no further cores are started.

## 020 – Capabilities and ownership IPC
**Decision:** Programs reach anything only through *handles* – slots in a per-process table in the kernel (index + generation, so a stale handle stays dead when its slot is reused; host-tested crate `capability`). Objects: `Endpoint` (a rendezvous point; handles are *receiving* or *sending*, the latter carry a badge), `Memory` (physical pages with exactly one owner) and `Console` (the kernel's text output). Talking is synchronous: `call` blocks until the receiver's `reply`; `receive` blocks until a call arrives. Decided together with the owner:
- *Messages are registers only* (N1): four words plus at most one attached handle. The kernel never copies payload – data travels only as memory objects. Ownership is therefore the *only* way to share data.
- *Owning means being mapped* (M1): a memory object is always mapped where its owner (or, during a call, its borrower) can use it. The kernel picks the address in a per-process mapping area (`0x1000_0000_0000`, a guard page after each object) and reports it with the message. Rust's rules, enforced by the page tables on every core (shootdowns, 019): *move* – unmapped from the sender, the receiver's now; *lend `&`* – read-only for both until the reply; *lend `&mut`* – unmapped from the lender, writable for the borrower until the reply. Borrowed memory can't be passed on; replies can't lend (nothing would end the borrow).
- *`write` is gone; a `log` service prints* (L1): only `log` holds the `Console` handle. Programs lend `log` a page with their text (`userlib`'s `println!`); `log` prefixes the name from the sender's badge – the kernel badges each program's handles with its name (8 bytes packed into the `u64`), so names can't be faked.
- Every program starts with the handles the kernel gives it as 0, 1, 2, … (handle 0 = `log` for everyone but `log`). The wiring lives in `kernel/src/ipc/checks.rs`.
- All IPC runs under the scheduler lock, since it changes several tasks at once (states, saved frames) – one atomic step on all cores. Results are written straight into the waiting task's saved `InterruptFrame`, which `block` records under that same lock, so a reply from another core can never miss it.
- A program that dies while owing a reply (e.g. after a fault in borrowed memory) hands lent memory back; its caller gets `ERROR_PEER_GONE`. Memory objects are unmapped before their process's address space is freed, so frames are freed exactly once.
- `userlib` mirrors the rules in types: lending takes `&Memory`/`&mut Memory` for the duration of the call, moving takes the `Memory` by value – the compiler refuses what the page tables would stop.
**Why:** The heart of DECISIONS 012. Registers-only messages keep the kernel tiny and make zero-copy the normal case; "owning = mapped" makes the ownership state visible in the one place the hardware enforces. Proven at every boot: `owner` lends `&mut` to `shout` and gets its text back upper-cased, lends `&` to `vandal` (which writes, is stopped, and owner's page is unchanged), `giver` moves a page and is stopped when it reaches for it, `intruder` forges handles. While lending, the kernel also asserts that the lender's own mapping really is gone or read-only – the lender is blocked in `call` and can't try itself.
**Alternatives:** A kernel-copied message buffer (comfortable for small text, but a second data path). Explicit `map(handle, address)` calls (flexible, but owning and accessing come apart). A user-space serial driver with an I/O-port capability (the "pure" way – comes with the first real driver). Asynchronous queues (no blocking, but buffering in the kernel and harder ownership).
**Limits:** One call at a time per server (`reply` before the next `receive`). A caller of an endpoint whose server died waits forever. No timeouts. Memory objects ≤ 1 MiB; mapping addresses are never reused. Capabilities can't be revoked.

## 021 – IPC without the training wheels: reply handles, timeouts, revocation, init
**Decision:** The limits of 020 are gone, decided together with the owner:
- *Reply handles* (R1): `receive` hands out a one-shot `Reply` capability with every message; `reply(reply_handle, …)` uses it up. A server can hold any number of unanswered calls and answer them in any order – or move a reply handle to someone else, who then answers. A borrow belongs to its reply handle: it ends with the reply, or when the handle is dropped or its holder ends (the caller gets its memory back and `ERROR_PEER_GONE`). The directory service shows it off: a lookup for a name not registered yet is parked and answered once the name shows up.
- *Closed endpoints* (a bug fix, no choice): an endpoint counts its receiving ends. When the last one goes (dropped, or its process ended), the endpoint is closed: waiting callers get `ERROR_PEER_GONE` at once, later calls fail at once.
- *Timeouts* (T1): `call` and `receive` take a timeout in ticks (`rcx`, 0 = none) and give up with `ERROR_TIMED_OUT`. For `call` it covers only the time in the queue: once a server took the call, the caller waits for the reply or the reply handle's loss – a timeout then would mean tearing lent memory out of a server mid-work. Expired waits are found by the scheduler on every switch.
- *Revocation per badge* (W1): who holds a receiving end can `mint(end, badge)` new sending ends and `revoke(end, badge)`: the endpoint bumps a generation for that badge, so every sending end minted before – and every copy of one, since copies keep badge and generation – fails with `ERROR_REVOKED`. Memory needs no revocation: one owner, and borrows end by themselves.
- *init in user space* (S1): the kernel starts exactly one program, `init`, with the console and one `Program` capability per built-in image. `call(program, lend(&list), [n])` starts a process whose handles 0…n−1 are the ones the list names (copied or moved) – nothing else. The caller gets a `Child` capability; `call(child)` waits until it ends and says how (exit code, or the CPU exception that stopped it). `init` makes the endpoints, mints badged sending ends (the log names come from them), starts everything and checks how the test programs ended; the kernel's boot check only looks at init's exit code. A `directory` service lets services register under a name and clients look them up.
**Why:** A capability system where the kernel wires everything up at boot isn't one yet – policy belongs in user space. Reply handles make the "duty to answer" an owned thing, which fits the ownership model and removes the one-call-at-a-time limit. Per-badge revocation needs almost no kernel state (a generation counter per badge) and gives a server exactly the tool it needs: shut out one client.
**Alternatives:** A per-server list of open calls, replied to by caller number (simpler, but numbers aren't capabilities and can't be handed on). Timeouts that also end delivered calls (T2: harsher, every server could crash mid-work). A derivation tree for fine-grained revocation like seL4 (much more bookkeeping), or closing whole endpoints only (coarse). A kernel name service (policy in the kernel).
**Limits:** Starting a program loads it while holding the scheduler lock – all cores pause scheduling for that moment. At most 16 handles per start; memory objects can't be passed at start (no address space yet to map into). The directory has 16 names and 16 parked lookups; names are first come, first served. Exit records of user programs are kept forever (a few bytes each).

## 022 – Polish: no "for now" limits where none are needed
**Decision:** Owner's rule: known limits are removed before new features. This round:
- *Starting a program no longer stalls the machine:* three steps – check the request (scheduler lock), load the ELF with **no lock held and interrupts on** (the task may even be preempted and move cores; its frame stays on its own kernel stack), then check again and hand over the handles (lock). No limit on the number of handles (the list is lent memory of any size), and memory objects can be passed at the start too; the child finds them with `memory_info` (`Memory::from_start_handle`).
- *Exit records* are kept only while someone can ask: dropping the `Child` handle (or its holder ending) forgets the record, or makes sure none is kept.
- *Addresses of memory objects are never reused – on purpose:* a pointer into memory that was moved away or given up keeps faulting forever instead of one day pointing into another object (use-after-free). What made fresh addresses expensive was the page tables piling up; now tables that become empty are freed (`Mapper::unmap_and_prune`, after the TLB flush). In the upper half the level-3 tables stay, since every address space shares them. (A first try reused addresses; the boot test caught it: `giver`'s next page landed at its old address and the stale read succeeded.)
- *Shootdowns cover ranges:* one request for many pages (from 32 pages on, the targets reload CR3 instead of `invlpg` each). The heap's unmap is allocation-free (frames buffered on the stack) because the heap calls it while holding its own lock.
- *Kernel stacks have guard pages:* every task and core stack lives in a 64 KiB slot (top 64 GiB of the heap's entry) with only its top mapped; slots are reused. The boot stack's lowest page is unmapped. An overflow faults; the CPU can't push that fault's frame onto the broken stack and raises a double fault on its own stack, which is reported. A new crash test (`--crash-stack`) proves it at every `cargo xtask test`.
- *Stopping other cores uses an NMI*, which even a core spinning with interrupts off can't ignore; an NMI that isn't ours is reported and ignored (it's no program's fault).
- *A core that doesn't start* is put back to sleep (INIT) and skipped; the others still start.
- Smaller: `log` points its own `println!` at the console (same message format) so it can print; the identity map's tables are freed; the "top-level entries fixed once processes exist" invariant is now checked by `paging::map` instead of trusted; memory objects up to 256 MiB.
**Why:** Each of these was a caveat someone picking the project up would trip over; none needed a design change.
- *Programs' stacks grow:* 16 KiB are mapped at the start, the rest of an 8 MiB stack room appears page by page when touched (the page fault handler maps it and the instruction runs again). Its lowest page is never mapped, so an overflow of all 8 MiB still ends the program. `hello` recurses ~100 KiB deep at every boot.
- *Programs have a heap:* `userlib` brings `alloc` (`Box`, `Vec`, `String`) using the kernel's own `heap` crate; its pages are memory objects. Freeing a large block gives its object back – a registry of (address, handle) pairs, in a memory object of its own that doubles when full, finds the handle. The directory now keeps any number of names and parked lookups.
- *The heap gives memory back:* small blocks now come from *slabs* – runs of pages aligned to their own size (one page up to 256-byte blocks, up to 8 pages for 2 KiB blocks, so ≥ 16 blocks each). A slab's bookkeeping sits in its first block(s); the slab of any block is its address with the low bits cleared, so freeing stays O(1) without a side table. An empty slab goes back to the page source; one empty slab per class is kept, because in the kernel every unmap is a shootdown to every core – freeing it right away turned an allocate/free per task switch into a shootdown storm at 80 cores. The page source now takes an alignment, which also lifts "alignment > 4 KiB refused": large blocks get exactly the alignment asked for (`memory_new` takes an alignment for programs).
- *Up to 256 cores, x2APIC:* core sets are 256-bit (`scheduling::cores`, plain and atomic, host-tested). The APIC driver uses x2APIC mode (registers as MSRs, 32-bit APIC IDs, the interrupt command one 64-bit MSR) whenever the CPU has it – which firmware that switched to it already requires. A started core enables its APIC in the boot core's mode *before* it counts as online: it may send a shootdown right away, and an x2APIC MSR access on a still-xAPIC APIC faults. (Found by booting 4 x2APIC cores: that fault, then the stop NMI faulting the same way, hung the machine silently – so kernel exceptions and panics are now reported *before* other cores are stopped.) Shootdowns re-send their IPI to cores that take too long, so a lost IPI can't hang a core.
- *Timer ticks only try the run queue:* a tick is a chance to switch, not a duty; if another core holds the scheduler lock, the current task runs one more tick. Voluntary switches (sleep, exit, IPC) still wait for the lock. The timeout scan runs only when a deadline is due and walks tasks without allocating. With 80 cores this took the boot from over 200 s (79 cores queued at one lock every tick) to 6 s. `cargo xtask test` boots 80 cores in x2APIC mode every time.

## 023 – The screen: device memory is owned memory, the first driver lives in user space
**Decision:** Hematite draws on the screen the firmware set up. Decided together with the owner: the driver runs in user space, it gets the screen as a capability, and clients lend it their pixels.
- *Finding the screen:* the loader reads the current mode of UEFI's Graphics Output Protocol (no mode switch – the firmware picked one that works with the attached screen) and passes `boot_info::Framebuffer`: address, size, width, height, stride, pixel format. Only page-aligned 32-bit RGB/BGR framebuffers count; bit-mask and "blit only" modes mean "no screen".
- *Caching per mapping* (also issue #7): `paging::Flags` carries a `Caching` – write-back, write-combining or uncached – encoded in the PWT/PCD bits. Every core loads the same page attribute table (`x86::pat`): the power-on table with entry 1 (PWT only, formerly write-through, unused) turned into write-combining – Linux uses the same slot. The PAT bit itself is never used (bit 7 in a 4 KiB entry, bit 12 in a 2 MiB one). The loader maps every 2 MiB of the physical memory window that holds no RAM as uncached, instead of trusting the firmware's MTRRs, and leaves the framebuffer out of the window (and of the temporary identity map) entirely – its only mapping is the owner's, so there are never two views with different memory types (Intel discourages that, SDM §11.12.4), and the kernel can't touch the screen even by mistake (it checks at boot). Where the framebuffer starts or ends inside a 2 MiB page, the rest of it is mapped page by page. The mapper refuses to map a frame again with different caching.
- *Device memory is a memory object* (`kernel/src/ipc/memory.rs`): RAM or a fixed device range. The same ownership rules apply – one owner, move, lend `&`/`&mut`, enforced by the page tables – and every mapping uses the object's caching. It is never zeroed and never freed (the frame table doesn't know it). Kernel objects that read lent memory through the window (console, program start) refuse device memory.
- *`Device` capabilities:* the kernel gives `init` one per device (today: the screen) – an unopened memory object plus four words describing it. `call(device)` opens it: the handle becomes an owned memory object mapped into the caller (the kernel checks the caching in the page tables), the reply brings width, height, stride and pixel format. `init` only moves the handle to `display`, it never opens it.
- *The `display` service* owns the screen; nobody else can touch it. Protocol (`userlib::display`): `INFO` (size), `DRAW` (lend `&` pixels as `0x00RRGGBB` rows, an area; cut to the screen). It converts to the screen's byte order and ends each draw with `sfence`, so the write-combining buffers are flushed before it replies. `paint` draws the first picture through it.
- *Proof from outside:* after a normal boot test, `xtask` asks QEMU's monitor for a `screendump` and checks two pixels of paint's picture (top-left background, red streak in the centre).
**Why:** A driver is just a program that owns a device – and since owning memory is already a capability with Rust's rules, owning the framebuffer needs no new kernel concept besides "open". Device-specific code (pixel formats, clipping) stays out of the kernel. Write-combining instead of uncached makes framebuffer writes burst instead of one bus transaction each. Lending pixels `&` means the display can't scribble on a client's memory, and the client can't touch the screen. The screenshot check can't be fooled by a program that only *says* it drew.
**Alternatives:** A kernel text console on the framebuffer (simplest, but a driver in the kernel). A generic "map physical range" call (any holder could map anything). Write-combining via MTRRs (few, global, owned by the firmware). Clients writing into shared screen memory directly, compositor style (faster for animation; later, with damage tracking). Choosing a resolution with GOP `SetMode`.
**Limits:** One screen, in the firmware's mode. `display` serves one request at a time and copies whole areas (no double buffering, no damage tracking).

## 024 – Kernel bugs take down as little as provably safe
**Decision:** Decided together with the owner (issue #5): a CPU exception in kernel mode or a `panic!` no longer always stops the machine.
- *The rule* (`kernel/src/task/faults.rs`): only the current task ends – a kernel task, or the user program whose system call it was (`Exit::KernelFailed`, for programs `abi::CHILD_KERNEL_FAILED` with the exception or `abi::KERNEL_PANIC`) – if **interrupts were on** where it failed, and it isn't one of the kernel's own tasks (boot, idle; `TaskContext::essential`). Otherwise – and always after a double fault or a machine check – the machine stops as before, and the report now says why.
- *Why interrupts are the proof:* every `SpinLock` switches them off while it is held, and interrupt handlers run with them off. Interrupts on means this core holds no lock and handles no interrupt, so no shared structure is half-changed by it – the failed code was only working on its own stack. That covers kernel tasks and the parts of system calls that run with interrupts on (loading a program); IPC runs under the scheduler lock and still stops the machine if it fails.
- *The price:* there is no unwinding (`panic = abort`), so whatever the task owned on its kernel stack is leaked – a leak, not corruption; the report says so.
- *A smaller kernel:* after boot the boot task ends (the "Still alive" heartbeat is gone). From then on the only kernel tasks are the idle tasks; everything else is a user program.
- *Proven at every boot:* `task::check` spawns a kernel task that reads unmapped memory and one that panics; both must end as `KernelFailed` and the boot goes on. The `--crash` test now faults in a kernel task *while holding a lock* – that must stop the machine; `--crash-stack` (double fault) too.
**Why:** Owner's rule: robustness before features. A kernel bug a program can trigger shouldn't let it take the whole machine down when the kernel can prove nothing shared is damaged. Using the interrupt flag as proof needs no new bookkeeping and is stricter than counting locks (it also excludes interrupt handlers).
**Alternatives:** Keep stopping on every kernel bug (safe, but one bug = whole machine down). Count held locks per core (needs per-core state even before the GDT is ours, and misses interrupt handlers). Restartable kernel tasks with a supervisor (few kernel tasks left to restart; restarting services belongs in user space, e.g. `init`). Unwinding (big runtime, against "no big external crates").
**Limits:** A contained task leaks what its kernel stack owned. Lock-free code that runs with interrupts on and spans several steps would not be protected by this rule – there is none today; new code like that must keep interrupts off or tolerate being cut off.

## 025 – The keyboard: an interrupt is a reply, ports are a handle
**Decision:** Decided together with the owner (milestone "keyboard", option A): hardware interrupts reach user space as IPC, and the keyboard is driven by a user program.
- *Interrupts as replies* (`kernel/src/ipc/interrupt.rs`): an `Interrupt` handle stands for one device line. `call(interrupt)` blocks until the line fires; the reply's word 0 says how often it fired since the last call. Fires while nobody waits are counted, not lost. A timeout works as for queues. The handle can be moved, not copied: one line, one driver. The kernel's whole share is: acknowledge the interrupt at the local APIC, wake the waiting driver. No signals, no callbacks, no kernel-side driver code – a driver is a loop of calls, like any server.
- *I/O APIC* (`kernel/src/arch/io_apic.rs`, format in `x86::io_apic`, wiring from the ACPI MADT in `acpi`): at boot every line of every I/O APIC is masked; only lines handed out are routed. ISA IRQ `n` arrives on vector `0x50 + n`; ACPI interrupt source overrides say which input an IRQ really is and how it signals. Each routed line goes to the next online core in turn, starting with the second (the first keeps the clock). A level-triggered line is masked when it fires and opened again by its driver's next `call` – "done with the device"; edge-triggered lines stay open, since a masked edge is lost for good.
- *Ports as a handle* (`kernel/src/ipc/ports.rs`): a `Ports` handle covers a few I/O ports (first port + bitmask: the keyboard controller gets 0x60 and 0x64, not the speaker port 0x61 in between). One `call` runs up to four byte reads and writes (`abi::run_port_ops`, shared by kernel and host tests); a read can depend on the one before it ("read the status, and the data only if there is any"), so the keyboard driver needs one call per byte, without a race between status and data. Small choice, decided alone: a per-program I/O permission bitmap in the TSS would let drivers use `in`/`out` directly, but needs an 8 KiB bitmap per program swapped on every task switch on every core. A kernel call per byte costs microseconds – nothing for a keyboard – and keeps "everything is a call on a handle" exact to the single port.
- *Programs:* `keyboard` holds the interrupt and the ports, turns scancodes (set 1, extended keys included) into keys and calls its listener with each: characters, or edit keys (arrows, Home, End, Delete; `userlib::keyboard`). Layouts are data (`programs/keyboard/src/layouts.rs`): US (default) and German with AltGr; Alt+Shift switches, as on Windows – a scancode names a key's position, the layout its meaning. `terminal` is the listener: a strip at the bottom of the screen showing the line being typed (with a cursor that moves) and the last three, drawn through `display` like `paint`; Up and Down bring earlier lines back. `init` connects the two with an endpoint of their own and starts them after paint, so the strip lies on top of the picture. The 5×7 font moved to `userlib::font`, shared by paint and terminal.
- *Proven at every boot:* the boot test types through QEMU's monitor (`sendkey`, real PS/2 scancodes through the real interrupt path): a line in the US layout, Alt+Shift, a German line using arrows, Home/End, Shift, AltGr and an umlaut, then Up + Enter – and waits for each line in the log; the screenshot check also looks at the terminal strip.
**Why:** The keyboard is the first device that *talks first*. Making its interrupt a reply reuses everything IPC already has – blocking, timeouts, ownership of handles – instead of a second mechanism; microkernels like seL4 do the same ("notifications"), textbook kernels mostly handle the keyboard inside the kernel.
**Alternatives:** Kernel keyboard driver feeding a buffer (simple, but device code in the kernel and against DECISIONS 023's direction). Signals/upcalls into the driver (a second way to deliver events, with reentrancy problems). I/O permission bitmap (see above). A legacy PIC route instead of the I/O APIC (works only on the boot core's old wiring and is going away on new machines).
**Limits:** Only the 16 ISA IRQs can be handed out – lines beyond need a device that uses them (PCI), which nothing finds yet. The level-triggered path (mask on fire, open on the next wait) is not exercised by any QEMU device we drive. The keyboard handle can reset the machine (command 0xFE on port 0x64) – the classic 8042 quirk, so `keyboard` is trusted with that. Accents (´ ` ^) are typed as themselves (no dead keys); the layout is chosen with Alt+Shift, not remembered.

## 026 – The shell: what it holds is all that exists for it
**Decision:** Decided together with the owner (milestone "shell", option A); the details below decided alone.
- *Its own program* (`programs/shell`), not part of the terminal: the terminal shows and edits text, the shell decides what a line means. They talk over the terminal's endpoint like any client.
- *No `PATH`:* `init` gives the shell a `Program` handle (a copy) for each program it may start, and a page with their names. `help` lists exactly those; any other word is "no such command or program". Which handles a started program gets is the shell's choice per program (`programs/shell/src/programs.rs`) – always a copy of the shell's terminal handle as handle 0.
- *Output goes where handle 0 points:* the terminal speaks the log's protocol (a page lent `&`, word 0 = length), so `println!` in a program started by the shell lands on the screen without the program knowing. The same binary started by `init` prints to the log. Redirection is choosing a handle.
- *Terminal protocol* (`userlib::terminal`): text lent `&` = output; `READ_LINE` with a page lent `&mut` = "give me the next finished line" – the reply is parked until Enter (like the directory's lookups), lines typed meanwhile wait in order (type-ahead); `CLEAR` without attachment. The terminal tells requests apart by the attach mode, never by a word that could be a text length. Keys count only from the badge "keyboard" – a program holding the terminal can read lines but not type into it.
- *Ends are reported, the shell goes on:* exit code, the exception the kernel stopped a program for, or a contained kernel failure (DECISIONS 024).
- *Stopping a program* (`kernel/src/ipc/stop.rs`): whoever holds its `Child` handle – its parent, nobody else – may `call(child, [CHILD_STOP])`. The program ends the next time it would continue in user mode: the scheduler, about to run it, ends it instead (and the interrupt path catches one that runs on undisturbed). Waits that a timeout could cut short (queues, children, interrupts, sleep) are cut short; a program waiting for a *reply* waits on, because a server may hold memory it lent – it ends right after the reply. `CHILD_POLL` asks without waiting, `CHILD_WAIT` takes a timeout.
- *Jobs and Ctrl+C:* `name &` runs a program in the background as a numbered job; `jobs` lists them, `stop <n>` stops one, and before each command the shell reports the jobs that ended (as Unix shells do before a prompt). A foreground program is waited for 50 ms at a time; in between the shell asks the terminal whether Ctrl+C was pressed (`TAKE_INTERRUPT`) and stops it if so. The keyboard driver types Ctrl+letter as the old ASCII control characters.
- *Arguments are a handle too:* the rest of the command line goes to a program that takes arguments as a page of text (today `count`, which counts slowly – something to run in the background and to stop).
- *Typing felt slow – measured, not guessed:* from the keyboard interrupt to the terminal took ~0.25 ms, but redrawing the whole strip (1.2 MB of pixels) in an unoptimized debug build took ~113 ms per key. Now the programs that push pixels (`userlib`, `display`, `terminal`, `paint`) are optimized even in debug builds (workspace `Cargo.toml`), and a key that only changes the line being typed redraws only that line: ~1.7 ms per key.
- *Proven at every boot:* the boot test types `help`, `hello` (its output must appear on the terminal, ending with "exit code 0") and `intruder` (must be reported as stopped by a page fault).
**Why:** In a capability system a shell can't be "a program that can run anything" – that would be ambient authority with extra steps. Holding exactly the programs it may start makes the security model visible at the prompt. Making the terminal speak the log's protocol turns output redirection into handing over a different handle, with no new mechanism.
**Alternatives:** Shell inside the terminal (one program less, but editing and meaning tangled, and no way to give programs the terminal without the shell). A shell that asks the kernel for programs by name (a global namespace the kernel would have to keep). Programs printing to the log and the shell copying it (all output mixed, no per-program redirection).
**Limits:** Job ends are reported at the next command, not the moment they happen (the shell waits in one place at a time – no waiting on several things at once yet). Ctrl+C reaches a foreground program within 50 ms. A program blocked on a reply that never comes can't be stopped. Readers of the terminal take turns for lines.

## 027 – Waiting for several things at once: `send`, and answers in a mailbox
**Decision:** Decided together with the owner (option B of three): a call can be made without waiting for it, and its answer arrives later as a message.
- *`send(object, attachment, words, mailbox, tag)`* is a `call` that returns at once. The *mailbox* is an ordinary endpoint the sender holds a receiving end of; the answer – the reply, or why there is none (`ERROR_PEER_GONE`, `ERROR_REVOKED`, …) – is queued there as a message without a reply handle, the chosen tag in `rdi`, its status in `r14`. So `receive` now brings two kinds of message: calls (with a reply handle) and answers (without). One queue holds both, in order.
- *Everything one waits for answers the same way:* `send(child, [CHILD_WAIT])` answers when the child has ended (at once if it has – its end and its exit record are one step under the scheduler lock, so nothing slips between), `send(interrupt)` when the line fires. Objects that answer at once (console, programs, devices, ports) stay `call`-only.
- *In the kernel, a caller is either waiting or on its way* (`object::Caller`): blocked in `call`, the result goes into its saved frame; after `send`, it is posted to its mailbox (`delivery::post`, which hands it straight to a receiver waiting there). A `call`er is blocked, so its attachment stays put until delivery (as before). A `send`er runs on, so its attachment is taken from it at once and travels with the message (`transfer::Carried`): moved things leave its table, lent memory is restricted in its page tables right away (`&` read-only, `&mut` unmapped). If the call fails before delivery, moved things are given up as a `drop` would, lent memory goes back.
- *Lent memory outlives its lender:* memory objects are shared as `Arc<Memory>`, and the borrow (`Lend`) holds a reference. A lender that ends while its memory is lent no longer pulls the frames out from under the server; they are freed when the borrow ends. That made the second limit of 026 removable: *stopping a program cuts even a reply wait short.* Waiting for a reply is now explicit (`Waiting::ForReply`); a reply that finds nobody waiting returns `ERROR_PEER_GONE` to the replier, who keeps its attachment. The terminal uses that: a reader that was stopped doesn't take the next line with it.
- *`userlib`:* `Mailbox` (`new`, `send`, `receive` → `Incoming::Call` / `Incoming::Answer`), `Send` (memory by value), `Pending`, which holds lent memory until its answer came – then `finish()` gives it back. So safe code can't touch memory the kernel has taken away, even though the sender runs on. Helpers: `watch(child)`, `interrupt::watch`, `terminal::request_line` / `line_in`, `terminal::watch_interrupt`.
- *The shell* waits in its mailbox for the next line, the next Ctrl+C (the terminal's `WAIT_INTERRUPT` is parked until Ctrl+C, replacing the polled `TAKE_INTERRUPT`) and every program's end. A job's end is reported the moment it comes; Ctrl+C acts at once instead of within 50 ms. The keyboard driver waits for its interrupt through a mailbox too, so that path runs at every boot.
- *Proven at every boot:* `count 2 &` must be reported as ended without anything typed; `ask` (new: asks for a line, i.e. waits for a reply only Enter brings) must be stopped by Ctrl+C, and the next line (`jobs`) must reach the shell.
**Why:** Everything in Hematite already was "a message over a handle" – a reply, an interrupt, a child's end. Making each of them a message that can arrive in one place keeps one mechanism instead of adding a second (an event object beside messages). And the ownership rules carry over untouched: the page tables enforce a borrow whether or not the lender is blocked, so asynchrony costs no new safety argument – only that lent memory may outlive its owner, which an `Arc` per memory object settles.
**Alternatives:** A wait set (A: `epoll`-like; handles in, "this one is ready" out – but then the result still has to be fetched with a second call, and it doesn't cover calls where we are the caller). Threads (C: one per wait – the heaviest tool for this, and issue #3 is its own design question). Polling with timeouts (what the shell did; costs latency and wakeups).
**Limits:** A sent call can't be taken back: it waits until a server takes it or its endpoint closes – there is no timeout for `send` (the answer can be ignored). Mailbox queues have no bound. Dropping a `Pending` before its answer keeps lent memory away for the rest of the program.
